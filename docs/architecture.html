System design · WooCommerce on Kubernetes · Team MCP gateway

One MCP endpoint in front of every server the team uses

Author: Prachi

A WooCommerce store runs in a Kubernetes cluster next to a gateway. Admins register MCP servers once; every member reaches all of them through /mcp with a personal API key, from an MCP client or from a chat agent in the dashboard. Members never see the servers' credentials, and every call lands in an audit log.

Tools named <server>__<tool>Two servers can share a tool name; one can never shadow another.
Gateway's own credential per serverClient keys are never forwarded, so one bad server cannot collect them.

SQLite on a volumeSimple for one replica; scaling out would need Postgres.
Setup Job, not init containerWordPress writes its files when its own container starts; the Job waits for them.

LLD 3

Chat agent: the tool loop runs inside the gateway

ConcernHow it is handled
Acts as the logged-in userThe session cookie gives user A; every call goes through GatewayService with A as caller, source chat.
LLM providerAny OpenAI-compatible /chat/completions: base URL, model, key. Here Groq, openai/gpt-oss-120b, temperature 0.
LLM keyLLM_API_KEY in Secret gateway-secrets; never in the browser or a prompt.
NetworkGateway egress allowed to HTTPS on public addresses only, and only when a model is configured.
Prompt injectionTool descriptions and results reach the model only as tool data; the system prompt says they are not instructions; results truncated; every call shown to the user.
Disabled or dead serverIts tools are not offered in the next question.
